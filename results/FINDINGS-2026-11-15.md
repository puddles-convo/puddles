# Findings of 15 November: reproduction, the proposer's toolbox, and our own Qwen helper

Status at 11:35 PST. The two training loops are still running; their rounds so far are below and in the run journal, [`toolbox-2026-11-15/RUNLOG.md`](toolbox-2026-11-15/RUNLOG.md), which records every step with its cost.

## In one paragraph

**Last night's self-improvement result reproduces.** Measured again 10 times on scenarios no gatekeeper used, the loop's final policy beats its starting policy by **+0.63 (95% interval +0.53 to +0.73)**, higher in **10 of 10** sets, and beats a helper with no conversation rules by **+0.25 (+0.15 to +0.37)**, also in 10 of 10. We also built a **toolbox** for the proposer (rules, skill cards, examples) and started a like-for-like comparison against the rules-only loop; after 3 rounds each, both arms kept the same kind of change in round 1 and nothing since, so there is no result on the toolbox yet. Finally, the loop now runs end to end with **our own Qwen3.5-9B helper on Modal**, which starts far lower than gpt-6-luna and failed one medication safety case in its only complete round.

## 2. The proposer's toolbox (in progress)

**What was built** (`PUDDLES_PROPOSER=toolbox`; prompt in [`docs/agents/t6c-proposer-toolbox.md`](../docs/agents/t6c-proposer-toolbox.md)):

| Tool | What changes in the helper's prompt |
|---|---|
| `edit_rule` | One Conversation rule (C) added, reworded or removed, as before |
| `add_skill_card` | One skill card (K): a named technique with when to use it, when not to, and 2 to 5 steps, citing this round's sources |
| `set_examples` | One Examples item (E): code picks 1 to 3 exchanges rated 5/5 by seekers from the ESConv **train** split; the model never writes them |

Each action is exactly one item edit on the policy file, so the gatekeeper, the decision log, the replay check, parking and memory work unchanged, and a policy without cards or examples is byte for byte as before. `train_adapter`, `merge_adapters` and `no_change` are not offered yet.

**The comparison.** Both loops run at the same time, on the same code and models, from `policy-v1`, with last night's gate settings. They differ only in the proposer.

| Round | Toolbox arm (`runs/luna-arm-toolbox`) | Rules only (`runs/repro-2026-11-15`, the reproduction) |
|---|---|---|
| 1 | **kept**: C1 reworded, quality 3.35 → 3.90 | **kept**: C1 reworded, 3.43 → 3.78 |
| 2 | reverted: **skill card K1** "Explore hesitation before planning", 3.75 → 3.53 | reverted: rule C9 on the same failure, 3.85 → 3.50 |
| 3 | reverted: C1 reworded again, 3.75 → 3.47 | reverted: C1 reworded, 3.85 → 3.43 |
| 4 | reverted: **examples E1** for "shame about needing support", 3.75 → 3.85 (+0.10, below the noise) | no candidate: the same-idea check refused a repeat of round 3 |

- After round 1 both arms had found and fixed the same weakness the same way, as last night's run did.
- In round 2 both arms found the same new failure independently (moving to action before exploring the person's hesitation) and fixed it with the tool each had; neither helped.
- The toolbox proposer has now used all three tools: rules twice, a skill card once, examples once.
- **A weakness of `set_examples` found in round 4:** the picker took a greeting as one of its exchanges ("Hi, I'm well thanks. How are you today?"). It takes the first exchange long enough in a top-rated conversation, which is often small talk. A better picker would skip the opening turns and match the exchange, not only the scenario, to the situation.
- **No conclusion on the toolbox yet.** The rule written before the runs: the toolbox counts as better only if "toolbox final minus rules-only final" is above zero over 40 scenarios under both judges (`scripts/arms_measure.sh`, run once both loops stop).
- Caps: the toolbox arm stops at 6 rounds or $5; the rules-only arm runs with last night's settings ($11 cap, no round cap), so it may run longer.

## 5. Limits

- All people in the conversations are a language model playing ESConv scenarios.
- The repeated measurement was scored by the loop judge only, not the independent `gpt-6-astra`.
- The strict grading guide was written last night and is not calibrated against human ratings.
- The starting policy's safety wording was rewritten by hand before last night's run and has not been reviewed by the team.
- Today's code includes integration's reply-trimmer change (#77), which last night's run did not have.
- C8 is protected in these runs (`PUDDLES_PROTECT_C8=1`), as last night; it is editable by default on `integration`.
- **Memory was off in both loops.** Every past.dev call returned `401 malformed-api-key`: the `PAST_API_KEY` used today is not a valid past.dev key. The loops are built to go on without memory (each read is logged as unavailable, each copy stays pending), so both arms ran with the history lists built from their own decision logs but without recall from past.dev. Both arms are equally affected; last night's run had working memory.
