# Findings of 15 November: reproduction, the proposer's toolbox, and our own Qwen helper

Status at 12:35 PST: all runs finished. Every step, with its cost, is in the run journal, [`toolbox-2026-11-15/RUNLOG.md`](toolbox-2026-11-15/RUNLOG.md).

## In one paragraph

**Last night's self-improvement result reproduces.** Measured again 10 times on scenarios no gatekeeper used, the loop's final policy beats its starting policy by **+0.63 (95% interval +0.53 to +0.73)**, higher in **10 of 10** sets, and beats a helper with no conversation rules by **+0.25 (+0.15 to +0.37)**, also in 10 of 10. We also built a **toolbox** for the proposer (rules, skill cards, examples) and ran it against the rules-only loop under identical conditions: after 11 rounds each, both kept one change and ended level (**+0.02, -0.15 to +0.19**), so one run per arm shows no measurable difference. The toolbox proposer produced more testable ideas (8 of 11 rounds against 5 of 11), and in both arms the gate's noise bar, not the proposer, was the limit. Finally, the loop now runs end to end with **our own Qwen3.5-9B helper on Modal**, which starts far lower than gpt-6-luna and failed one medication safety case in its only complete round.

## 2. The proposer's toolbox: no measurable difference after one run per arm

**What was built** (`PUDDLES_PROPOSER=toolbox`; prompt in [`docs/agents/t6c-proposer-toolbox.md`](../docs/agents/t6c-proposer-toolbox.md)):

| Tool | What changes in the helper's prompt |
|---|---|
| `edit_rule` | One Conversation rule (C) added, reworded or removed, as before |
| `add_skill_card` | One skill card (K): a named technique with when to use it, when not to, and 2 to 5 steps, citing this round's sources |
| `set_examples` | One Examples item (E): code picks 1 to 3 exchanges rated 5/5 by seekers from the ESConv **train** split; the model never writes them |

Each action is exactly one item edit on the policy file, so the gatekeeper, the decision log, the replay check, parking and memory work unchanged, and a policy without cards or examples is byte for byte as before. `train_adapter`, `merge_adapters` and `no_change` are not offered yet.

**The comparison.** Two loops at the same time, same code and models, from `policy-v1`, last night's gate settings; they differ only in the proposer. Both stopped by the same rule after 11 rounds: the proposer failed in 3 rounds in a row, each time refused by the same-idea check as a variant of an idea already rejected.

**What this does and does not show**

- With one run per arm the toolbox made **no measurable difference** to where the loop ended. It is **too soon to say the toolbox helps or hurts**: two runs of the rules-only loop alone ended 0.18 apart (last night's `policy-v4` and today's reproduction, same code and settings), as far apart as anything we could attribute to the toolbox.
- There is no sign that more tools confused the proposer: it produced a testable candidate in 8 of 11 rounds against 5 of 11 with rules only, and failed its checks less often. The rules-only proposer spent most of its second half re-proposing a rejected C1 idea.
- **The bottleneck was the gate in both arms.** Almost every candidate was reverted for "no gain above the noise" (0.275 on one set of 20); the best misses were +0.10 to +0.15.
- **Test A (do near-misses add up?): no.** The toolbox arm's final policy plus its two near-misses scored the same as without them. The sub-noise gains were most likely noise.
- Both of today's loops improved on the start (+0.45 to +0.47) but stopped below `policy-v4`, which remains the best policy measured.
- `set_examples` has a known weakness: its picker took a greeting as one exchange. A better picker would skip the opening turns.
- Next steps that would settle the question: 3 or more runs per arm; a gate that re-measures promising candidates on extra sets before rejecting them (a beam with confirmation); a better examples picker.
- Saved: every set's scores and the three policies in [`toolbox-2026-11-15/measurements/`](toolbox-2026-11-15/measurements/); `python scripts/repeat_stats.py results/toolbox-2026-11-15/measurements/heldout-sets` rebuilds the tables with no model call.

## 5. Limits

- All people in the conversations are a language model playing ESConv scenarios.
- The repeated measurement was scored by the loop judge only, not the independent `gpt-6-astra`.
- The strict grading guide was written last night and is not calibrated against human ratings.
- The starting policy's safety wording was rewritten by hand before last night's run and has not been reviewed by the team.
- Today's code includes integration's reply-trimmer change (#77), which last night's run did not have.
- C8 is protected in these runs (`PUDDLES_PROTECT_C8=1`), as last night; it is editable by default on `integration`.
- **Memory was off in both loops.** Every past.dev call returned `401 malformed-api-key`: the `PAST_API_KEY` used today is not a valid past.dev key. The loops are built to go on without memory (each read is logged as unavailable, each copy stays pending), so both arms ran with the history lists built from their own decision logs but without recall from past.dev. Both arms are equally affected; last night's run had working memory.
